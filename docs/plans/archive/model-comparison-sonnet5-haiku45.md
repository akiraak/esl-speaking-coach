# AI 生成箇所を Sonnet 5 / Haiku 4.5 / Gemma 4 で比較する — 調査プラン

## 目的・背景

アプリ内の Claude 呼び出しのうち 4 経路が `claude-sonnet-5` を使っている。これを
`claude-haiku-4-5` と **Google の `gemma-4-31b-it`** に置き換えられるかを実データで
比較し、**経路ごとに**採否を決める。

**比較軸は 2 つだけ: 文章のクオリティと、料金。** レイテンシは判断材料にしない。

料金は「安いモデルのほうが安い」と決め打ちしない。**haiku は単価が 1/3 だが、
プロンプトキャッシュの最小長の差で sonnet より高くつく部分がある**（後述）。
経路ごとに実測し、**高くなった経路はそのまま「高くなった」と記録する**
（結論が「置き換えない」でよい）。

TODO の「トピック生成を haiku4.5 に変更」は本プランの Phase 1 で扱う
（比較して合格したら実装まで行う）。

### Gemma を入れることの意味（先に確認しておく）

CLAUDE.md の音声レイヤの決定は「**会話相手を Claude に保てること**が決め手」で
下している（OpenAI Realtime / Gemini Live を不採用にした理由がこれ）。安い中国系
モデルの調査でも、会話ターンだけは同じ理由で「品質が並ばない限り踏み切らない」と
結論している（[cheap-chinese-ai-models](cheap-chinese-ai-models.md) Phase 4）。

**会話ターンを Gemma に置き換えることは、この決定を覆すことになる。** 本プランでは
判断せず比較だけを行い、Phase 4 で「クオリティが並んでいるか」を根拠に改めて判断する。
トピック生成・フィードバック・記憶ノートは会話相手そのものではないので、この論点の外。

| --- | --- | --- | --- | --- |
| 2 | 会話ターン | `claude-sonnet-5` | ストリーミング / `effort: low` / `max_tokens: 1024` / system に `cache_control` | **$0.20**（最大） |
| 4 | トピック生成 | `claude-sonnet-5` | 非ストリーミング / `effort: low` / structured outputs | $0.01 未満 |
| 5 | フィードバック | `claude-sonnet-5` | ストリーミング / `effort: high` / `max_tokens: 16000` / structured outputs | $0.06 |
| 6 | 記憶ノート更新 | `claude-sonnet-5` | ストリーミング / structured outputs / `max_tokens: 2000` | 小 |
| 7 | 会話の翻訳 | `claude-haiku-4-5` | 非ストリーミング / structured outputs / **effort 送らない** | $0.01 未満 |

**翻訳は既に haiku で運用できている**（2 か月弱の実績）。これが「haiku でも
structured outputs は破綻しない」という既知の足場になる。

## 比較するモデル

| モデル | 入手経路 | 単価（入力 / 出力 / 1M） | 備考 |
| --- | --- | --- | --- |
| `claude-sonnet-5` | Anthropic（現行） | $3 / $15（〜2026-08-31 は導入価格 $2 / $10） | 基準 |
| `claude-haiku-4-5` | Anthropic | $1 / $5 | 翻訳で実績あり |
| `gemma-4-31b-it` | **Gemini API**（`.secrets/gemini-api-key` が既にある） | **$0（無料枠・レート制限あり）** | Gemma 4 は 2026-04-02 リリース。dense 31B の instruction-tuned |

- Gemma は Gemini API 経由なら**トークン課金なし**（無料ティアはレート制限あり、
  有料ティアで上限が上がる）。サードパーティ（OpenRouter 等）の従量課金は
  $0.10 / $0.35 なので、**無料枠が使えなくてもなお sonnet の 1/17 程度**。
  本プランでは Gemini API 経由で評価し、従量単価は参考値として記録する
- 廉価版の `gemma-4-26b-a4b-it`（MoE。$0.07 / $0.30）もあるが、まず 31B で
  クオリティの上限を見る。31B が落ちるなら 26B を見る意味はない
- Gemma はオープンウェイトなのでローカル実行もできるが、31B を iPhone で動かすのは
  非現実的なので**本プランでは API 経由のみ**を対象にする

## モデル仕様の差（実装制約 — 比較の設計がこれに縛られる）

| 項目 | `claude-sonnet-5` | `claude-haiku-4-5` | `gemma-4-31b-it` |
| --- | --- | --- | --- |
| API 形式 | Anthropic Messages | 同左 | **Gemini API（別形式）** |
| **プロンプトキャッシュ最小長** | **1,024 トークン** | **4,096 トークン** | 実質なし（要確認） |
| `output_config.effort` | `low`〜`max` | **非対応（400）** | 概念なし |
| thinking | adaptive が既定 | adaptive 非対応 | なし |
| structured outputs | `output_config.format` | 同左 | **`responseMimeType` + `responseJsonSchema`** |
| system prompt | `system` | 同左 | **`system_instruction`** |
| 最大出力 / コンテキスト | 128K / 1M | 64K / 200K | Phase 0 で確認（会話 45K・フィードバック 5K 程度なので足りる見込み） |

- **Gemma 4 は structured outputs と system instruction をモデルレベルで持つ**
  （プロンプト工作ではない）。トピック生成・フィードバック・記憶ノートは
  `responseJsonSchema` で本番と同じスキーマを渡せる
- **API 形式が違うので、評価ハーネスに Gemini アダプタを新規に足す**必要がある
  （既存の `anthropicStream` / `openaiStream` は流用できない。Gemini API には
  OpenAI 互換エンドポイントもあるが、structured outputs はネイティブの
  `responseJsonSchema` のほうが確実）

### 会話ターンでは haiku のほうが高くなる部分がある

2 キャラ台本の system prompt は**約 2,000 トークン**。sonnet-5 の最小長 1,024 は
満たすが、**haiku-4-5 の最小長 4,096 は満たさない**。しかも**満たさないときは
エラーにならず黙ってキャッシュされない**（`usage.cache_read_input_tokens` が 0 になるだけ）。

30 ターンぶんの system prompt だけを取り出すと:

| | 単価 | 2,000 × 30 = 60K トークン |
| --- | --- | --- |
| sonnet-5（キャッシュ読み 0.1 倍） | $0.3 / 1M | **$0.018** |
| haiku-4-5（キャッシュ無効・満額） | $1 / 1M | **$0.060** |

**この部分だけは haiku が 3.3 倍高い。** 履歴（messages 側はどちらもキャッシュしていない）
と出力は素直に 1/3 になるので、会話ターン全体では下がる見込みだが、
「単価が 1/3 だから料金も 1/3」にはならない。

参考として「system prompt を 4,096 トークンまで増やしてキャッシュを効かせる」
（4,096 × $0.1/1M = $0.0004/ターン で、2,000 トークン非キャッシュより**安い**）が
ありうるが、プロンプトの水増しは品質リスクなので**本プランのスコープ外**とし、
数字だけ記録して判断材料にする。

### 事前見積もり（Phase 2・3 の実測で裏を取る）

[ai-cost-map](../specs/ai-cost-map.md) と同じ前提（15 分 / 30 ターン、履歴平均 1,500 ×
30 = 45K、system 2,000 × 30 = 60K、出力 100 × 30 = 3K、フィードバックは入力 5K /
出力 3K）で置き換えた場合:

| 経路 | sonnet-5 | haiku-4-5 | gemma-4-31b（Gemini API） | gemma（従量・参考） |
| --- | --- | --- | --- | --- |
| 会話ターン・履歴 45K | $0.135 | $0.045 | $0 | $0.005 |
| 会話ターン・system 60K | $0.018 | **$0.060（高くなる）** | $0 | $0.006 |
| 会話ターン・出力 3K | $0.045 | $0.015 | $0 | $0.001 |
| **会話ターン 計** | **$0.20** | **$0.12（−40%）** | **$0** | **$0.012** |
| トピック生成 | $0.01 未満 | $0.01 未満 | $0 | ほぼ 0 |
| フィードバック | $0.06 | $0.02 | $0 | $0.002 |
| 記憶ノート | 小 | 小 | $0 | ほぼ 0 |
| **LLM 4 経路 計** | **約 $0.27** | **約 $0.15** | **$0** | **約 $0.014** |

- Gemma が無料枠で回るなら **LLM のコストはゼロ**になり、1 セッションは
  STT $0.09 + TTS $0.05 だけの **約 $0.14**（現行 $0.42 の 1/3）になる
- ただし出力トークン数は**モデルによって変わる**（haiku は effort と thinking が無い分
  短くなる可能性が高い）。上表は「トークン数が同じなら」の机上値なので、
  **実測の `usage` で置き換える**

### effort を送れない（等価比較の設計）

会話ターンは `effort: low`、フィードバックは `effort: high` で運用している。
haiku へはどちらも送れない（400）。Gemma には概念自体がない。よって比較は
「**sonnet-5 は本番同一の effort、haiku と Gemma は effort なし**」という非対称な形で
行い、その旨を結果に明記する。`TranslationClient` が既にこの形で動いている。

## 評価方法

**既存の評価ハーネス `tools/model-eval/` を使う**（安い中国系モデル調査の Phase 5 で
作ったもの。会話ターンとフィードバックをカバー済み）。README のとおりリポジトリ外の
作業ディレクトリへコピーして実行し、`run_*.mjs` の `providers` 配列に haiku と Gemma を足す。

**クオリティ:**

- **機械チェック**（`checklib5.mjs` / `report5.mjs`）: タグ無し行・発話行数上限・
  `[end]` の誤出力 / 出し忘れ・CJK 混入・ピンイン・markdown / 絵文字・
  最終行が質問で終わるか。**致命的違反**（台本パーサを壊すもの）の率で比較する
- **ブラインド A/B**（`judge5.mjs`）: `claude-opus-5` が順序入替 2 回で判定し、
  不一致は tie。会話・フィードバック・マルチターン再生の 3 種。
  **3 モデルなので sonnet を基準に haiku / Gemma をそれぞれ当てる**（2 系列）
- 英文としての自然さ・言い回しの幅は目視も併用する（機械チェックは規約違反しか見ない）
- **日本語の質を別立てで見る**（Gemma で特に効く観点）。トピックのタイトルとフック、
  フィードバックの `summary` / `note`、翻訳相当の文面は日本語で出るため、
  英語が良くても日本語が不自然なら不採用になりうる

**料金:**

- 各生成のレスポンスから usage（入出力トークン、Claude はキャッシュ読み書きも）を保存し、
  **モデル別の実額**を集計する。特に haiku で `cache_read_input_tokens` が
  0 のままであることを確認する（想定どおりキャッシュが効かないことの裏取り）
- Gemma は無料枠なので実額は 0 になる。**消費トークン数と、レート制限に当たった回数**を
  記録し、従量単価での換算値も併記する（無料枠が使えなくなった場合の備え）

トピック生成・記憶更新はハーネス未対応なので、比較スクリプトを新規に足す
（どちらも非ストリーミング / structured outputs なので小さい）。

## Phase 分割

### Phase 0: 下ごしらえ

- DEBUG 管理画面からセッションを書き出して `fixtures/export.json` を用意し、
  `tools/model-eval/` を作業ディレクトリへコピー、system prompt 4 本を抽出
- **`lib.mjs` に Gemini API アダプタを追加**（`keys` に gemini を足す /
  `system_instruction` / `responseJsonSchema` / ストリーミング）
- 各 `run_*.mjs` の `providers` に haiku と Gemma を追加（**effort を送らない**形で）
- 生成結果に usage を保存して、モデル別の実額を集計できるようにする
- **Gemma のレート制限に合わせて待ちを入れる**（無料枠で 20 回 × 複数ケースを回すため）
- Gemma のコンテキスト長・最大出力を実測で確認する

### Phase 1: トピック生成（TODO の既存項目・最小リスク）

- 比較スクリプトを新規作成し、同一の直近トピック一覧で 20 回ずつ生成
- **合否基準（クオリティ）**: structured outputs 適合 20/20、3 件が互いに重複しない、
  直近トピックと被らない、**日本語のタイトル・フックとして不自然でない**（目視。
  Gemma はここが弱点になりうる）
- **料金**: 実額を記録する。sonnet / haiku はほぼ変わらず、Gemma は 0 の見込みなので、
  **判断はクオリティで行う**
- クオリティが同等なら**この Phase で実装まで行う**（`TopicSuggestionClient` の
  2 箇所 + `AIPricing` / ai-cost-map の更新。Gemma 採用なら Gemini のテキスト生成
  クライアントを新規に書く必要があるぶん工数が増える点も判断材料にする）

### Phase 2: 会話ターン（本丸・最大のリスク）

- 単発ターン（`run_gen5.mjs`）+ マルチターン再生（`run_replay5.mjs`）
- **合否基準（クオリティ）**（Phase 5 の方式を踏襲）:
  - 致命的違反率が sonnet-5 と同等（タグ無し行・発話行数超過・`[end]` の誤り・CJK は
    台本パーサを壊すので 1 件でも出たら要検討）
  - opus ブラインド A/B で明確な負けが無い（tie 以上）
  - **thinking / effort が無い影響**が会話の自然さに出ていないかを重点的に見る
  - Gemma は 2 キャラ台本（`Chobi:` / `Naruko:` タグ + `[end]`）を守れるかが最初の関門
- **料金**: usage 実測で 1 セッション換算の実額を出す。**haiku は system prompt 分が
  高くなる**ことを数字で確認し、全体で下がるのか上がるのかを結論づける
- 置き換えの判断は「**会話相手を Claude に保つ**」方針（冒頭）と併せて Phase 4 で行う

### Phase 3: フィードバック・記憶ノート

- フィードバックは `run_feedback5.mjs` を流用（実 transcript 4 本 × 3 生成）
- **合否基準（クオリティ）**: structured outputs 全回適合、指摘の的確さで
  opus 判定が tie 以上、**日本語の説明文が自然**、途中で切れない（`stop_reason` が
  `end_turn`。不具合 [feedback-truncated](../feedback-truncated.md) と紛らわしいので必ず確認）
- 記憶ノートは短い比較スクリプトで、要約の粒度と英語の質を見る
- **effort: high を送れない**ぶん、ここは haiku / Gemma が最も不利になると予想される
- **料金**: 実測。出力が短くなるぶん見積もりより下がる可能性がある

### Phase 4: 判断と実装タスク

- 経路 × モデルで「クオリティ（同等 / 劣る）× 料金（下がる / 変わらない / 上がる）」の
  表にまとめ、本プランへ追記する。**haiku のほうが高かった経路はその数字を明記して
  「置き換えない」と結論づける**（隠さない）
- 会話ターンを Gemma にする案は、クオリティが並んでいても
  「会話相手を Claude に保つ」方針を覆す判断になるので、**そこを明示したうえで決める**
- 採用する経路があれば**実装タスクを別に起こす**（本プランは調査で閉じる）

## 影響範囲

- **調査のみ。アプリのコード・既定モデルは変更しない**（Phase 1 で合格した場合の
  トピック生成だけは例外的にこのプランで実装する）
- 採用時に想定される変更点:
  - **Claude 系へ移す場合**: 各クライアントのモデル文字列
    （`TopicSuggestionClient` は 2 箇所、`SessionFeedbackClient.model` は 1 箇所、
    `ClaudeMessagesClient.TurnParameters`、`MemoryUpdateClient` は 2 箇所）と、
    **effort を送らない分岐**
  - **Gemma へ移す場合**: 上に加えて **Gemini のテキスト生成クライアントを新規実装**
    （現状 `GeminiTTSClient` しかない）。ストリーミング・structured outputs・
    usage 取得・エラー処理を書くぶん工数が大きい。会話ターンなら
    `ClaudeMessagesClient` の裏にプロトコル境界を切る必要もある
  - `Usage/AIPricing.swift`（haiku の単価表は翻訳用に既存。Gemma は新規）と
    `docs/specs/ai-cost-map.md` の #2 / #4 / #5 / #6 の行
  - 会話ターンを移す場合は CLAUDE.md の「技術スタック」「音声レイヤの方針」
    「Claude API の使い方」の記述（**会話相手を Claude に保つ方針の見直しを含む**）

## Phase 1 実施記録（2026-08-01）— トピック生成

**条件**: 本番 `TopicSuggestionClient` と同じ system prompt（`main.swift` で抽出。1,626 文字
≒ 約 400 トークン）・user メッセージ・スキーマ。5 パターン（3 件セット × 4 + 1 件補充 × 1）
× 4 生成 × 3 モデル = **60 リクエスト、全件成功**。sonnet-5 のみ本番同一の `effort: low`、
haiku / Gemma は effort なし。スクリプトは `tools/model-eval/run_topic.mjs` / `report_topic.mjs`。

### 機械チェック

| モデル | 違反なし | genre 不一致 | hook 20 字超過 | フェンス混入 |
| --- | --- | --- | --- | --- |
| `claude-sonnet-5` | **19/20** | 0 | 0 | 0 |
| `claude-haiku-4-5` | 14/20 | 2 | 5 | 0 |
| `gemma-4-31b-it` | 14/20 | 1 | 2 | **4** |

sonnet の唯一の違反はタイトル 17 字の "iPhone派?Android派?" で、実害はない。

### 料金（20 リクエストぶん）

| モデル | 入力 | 出力 | 20 回 | 1 回あたり |
| --- | --- | --- | --- | --- |
| `claude-sonnet-5` | 19,732 | 2,299 | $0.0937 | $0.00468 |
| `claude-haiku-4-5` | 14,328 | 2,146 | $0.0251 | $0.00125 |
| `gemma-4-31b-it`（Gemini API 無料枠） | 8,556 | 2,046 | **$0** | **$0** |
| └ 従量参考（OpenRouter 単価で換算） | | | $0.0016 | $0.00008 |

- 同じプロンプトでも入力トークン数が違う（sonnet-5 は新トークナイザで haiku の **1.38 倍**、
  Gemma は 0.60 倍）。単価だけでなくトークナイザも実額に効く
- トピック生成の system prompt は約 400 トークンで、**sonnet-5 の最小長 1,024 も下回るため
  元々キャッシュは効いていない**（この経路に限っては haiku のキャッシュ最小長の不利は出ない）

### 目視（機械チェックに出ない差）

- **sonnet-5**: タイトル・フックとも簡潔で自然。ジャンル指示に忠実
  （technology → 「iPhone派?Android派?」「LINEかInstagramか」「どっちのアプリが便利?」）
- **haiku-4-5**: フックが敬体で冗長（最長 24 字）。「イヤホンか スピーカーか」のような
  不自然な空白、半角「?」と全角「？」の混在。内容自体は具体的で悪くない
  （「駅前の工事現場」「エレベーターで靴を踏まれた」）
- **gemma-4-31b-it**: **「近所のコンビニコンビニ」を 4 生成中 3 回**出す語の重複バグ。
  フックが「〜してみよう」「教えて！」の勧誘形に偏り、全角「？！」を多用（既存トピックは半角）。
  technology ジャンルで「電子書籍か紙の本か」を 3/4 回選ぶなどジャンル解釈がずれる。
  語彙も狭い（食べもの → 「忘れられない味」「思い出の味」の 2 種類のみ）

### 実害の切り分け

- **genre 不一致（haiku 2 件）は実害あり**: 返る値が `genre_id` ではなく英語名
  （"food and eating"）になると `TopicCatalog.genre(id:)` で引けず、
  次回生成のジャンル除外が機能しなくなる
- **フェンス混入（Gemma 4 件 = 20%）は実害あり**: 本番の `parseResponse` は素の
  `JSON.parse` なので生成が失敗する。ただし ` ```json ` を剥がす前処理を足せば
  **20/20 復旧する**（JSON 自体は valid で、`stopReason` も `STOP`）
- hook の 20 字超過は表示上の実害が小さい（`lineLimit` を付けていないので折り返すだけ。
  カードが縦に伸びる）。指示追従性の指標としては有効

### 結論: トピック生成は `claude-sonnet-5` のまま。置き換えない

- クオリティは sonnet-5 が明確に上（機械チェック・目視とも）
- 節約は 1 回あたり $0.0035（haiku）〜 $0.0047（Gemma）。トピック生成はセッションあたり
  1〜2 回なので、**毎日 1 セッションでも月 $0.1〜0.2**。品質を落としてまで取る額ではない
- **TODO の「トピック生成を haiku4.5 に変更」はこの結果をもって見送り**とする

### Phase 2 以降への申し送り

- **実機の会話データ（`esl-sessions-*.json`）が要る。** シミュレータのデータは
  最長 9 発話・内容もテスト用で、会話ターンとフィードバックの評価には使えない
- Gemma のフェンス混入は会話ターンでも起きうる。台本パーサ（`Chobi:` / `Naruko:` /
  `[end]`）への影響を Phase 2 で必ず見る
- effort なしでも 3 モデルとも structured outputs 自体は破綻しない（フェンスを除けば
  スキーマ違反はゼロ）。Phase 3 のフィードバックでも同様と予想される

## Phase 2 実施記録（2026-08-01）— 会話ターン（単発）

### 実機データをやめて合成 fixture にした

実機の書き出しが用意できないため、**合成の会話履歴**（`tools/model-eval/synthetic/`）に
切り替えた。`SessionExporter.Export` と同じ形で書いてあるので既存の `build_fixtures.mjs`
がそのまま通る。会話 3 本 + 単語 1 本、学習者ターン計 29。

実会話ではないが、この用途ではむしろ扱いやすい:

- 評価ケースが狙う状況（STT ノイズ・一語返答・日英混在・語学質問・明示的な別れ・
  曖昧な終わり）を**意図的に仕込める**
- 学習者の英語に日本人学習者らしい誤り（冠詞落ち・時制の揺れ・和製英語「mansion」）を
  入れてある。Phase 3 のフィードバック評価で効く
- 実会話を含まないので**リポジトリにコミットでき、再評価で同じ条件を再現できる**
- 履歴内の AI ターンは台本規約に沿って手で書いた中立な内容。特定モデルの癖に寄せていない

**限界**: 実際の STT 誤認識の分布や、作者本人の話し方の癖は再現していない。
実機データが用意できたら同じケース定義で回し直せる（`build_cases_synth.mjs` の
セッション参照を差し替えるだけ）。

### 機械チェック（12 ケース × 3 生成 × 3 モデル = 107 生成）

`ScriptStreamChunker` は文字も数字も無い行を捨てるので、**「空行が混ざる」は本番では
実害がない**。実害のある違反だけで数えると:

| モデル | 実害のある違反なし | 台本を壊す違反 | 内訳 |
| --- | --- | --- | --- |
| `claude-sonnet-5` | 31/36 | **1** | 発話 3 行 1・最終行が質問でない 1・最終行以外に長い疑問文 3 |
| `claude-haiku-4-5` | **35/36** | **0** | 最終行以外に長い疑問文 1 |
| `gemma-4-31b-it` | **0/35** | **35** | 下記 |

**Gemma は会話ターンで完全に破綻した。** 台本規約（タグ付き発話行だけを出す）を一度も
守れず、35 生成すべてが致命的違反。実際の出力は markdown の箇条書きで「分析」を書き出す形:

```
*   Learner says: "Yes. I try to cook curry but I forget the rice."
*   Chobi should react warmly...
```

発話行数は 9〜56 行（上限 2）、CJK 混入も多発。**structured outputs を使えない経路
（会話ターンは自由文の台本形式）では Gemma は使えない**。Phase 1 のトピック生成で
まともに見えたのは、`responseJsonSchema` がスキーマを強制していたからだと分かる。

**haiku は sonnet より規約遵守が良かった**（台本を壊す違反 0 対 1）。これは事前の
予想と逆。ただし機械チェックは規約違反しか見ないので、会話としての面白さ・自然さは
別途 opus ブラインド A/B で見る必要がある。

### 料金（36 リクエスト = 12 ケース × 3 生成）

| モデル | 入力 | cache 読 | cache 書 | 出力 | 36 回の実額 |
| --- | --- | --- | --- | --- | --- |
| `claude-sonnet-5` | 12,786 | **82,727** | 4,771 | 2,100 | **$0.1126** |
| `claude-haiku-4-5` | 75,603 | **0** | 0 | 1,537 | **$0.0833** |
| `gemma-4-31b-it` | 68,192 | — | — | 1,126 | $0（従量なら $0.0072） |

### キャッシュの予想が実測で裏付けられた

- **sonnet-5 は効いている**（`cache_read_input_tokens` = 82,727）
- **haiku-4-5 は 0**。プランの予想どおり、system prompt 約 2,000 トークンが
  haiku の最小長 4,096 に届かず、**エラーも警告もなく黙ってキャッシュされない**

その結果、**haiku の節約は 26% にとどまった**（$0.1126 → $0.0833）。単価は 1/3 なのに
1/1.35 にしかならない。プランの事前見積もり（会話ターン全体で −40%）より**悪い**。
理由は明快で、sonnet が system prompt を 0.1 倍で読めるのに対し haiku は毎回満額だから。

### opus-5 ブラインド A/B（30 ペア。sonnet-5 vs haiku-4-5）

Gemma は台本が成立しないため対象外。順序を入れ替えて 2 回判定し、不一致は tie。

**haiku 14 勝 / sonnet 12 勝 / 引き分け 4 —— 総合では互角。** ただしケース別に偏りがある:

| ケース | 勝敗 | 傾向 |
| --- | --- | --- |
| `goodbye-explicit` | **sonnet 3-0** | sonnet は「福岡の夢を話してくれてありがとう」とその日の話題に触れて締める。haiku は「無難だが定型的で、盛り上がった話への言及がなく印象が薄い」 |
| `continue-deep` | sonnet 2-1（点差も 8-5 / 9-5 と大きい） | 深い履歴で sonnet が文脈を拾い、オープン質問につなぐ。haiku は学習者が既に言った内容と重複した質問を返しがち |
| `learnerfirst-open` | sonnet 2-1 | 開幕の作り |
| `continue-early` | **haiku 3-0** | 序盤の軽い応答 |
| `japanese-mixed` | **haiku 3-0** | 日英混在の受け方。Naruko が質問を引き継ぐキャラ配分が良く、記憶ノート（息子）も自然に活かす |

**体験上の重みが違う点に注意**: `goodbye-explicit` はセッションの最後に来るので印象に残りやすく、
`continue-deep` は長いセッションほど頻度が上がる。回数では互角でも、**sonnet が勝っている場面のほうが
体験に効く位置**にある。

### TTS で読みにくい記号（新たに見つかった観点）

音声で読み上げる前提なので、音にならない記号は品質に直結する。36 生成あたりの総数:

| モデル | ダッシュ（—/–） | 三点リーダ | 括弧書き |
| --- | --- | --- | --- |
| `claude-sonnet-5` | **0** | 0 | 0 |
| `claude-haiku-4-5` | **13** | 0 | 0 |
| `gemma-4-31b-it` | 0 | 17 | **135** |

**haiku はダッシュを多用する**（opus の判定でも「ダッシュ記号は TTS 向きではない」と指摘された）。
system prompt は「no markdown, no text in parentheses」と禁じているので、Gemma の括弧書き 135 は
規約違反でもある。この観点は `report_gen_synth.mjs` に組み込んだ。

### 結論（Phase 2）

- **Gemma は会話ターンから除外**。品質以前に台本形式が成立しない
- **haiku vs sonnet は回数では互角（14-12-4）だが、置き換えは見送る**のが妥当。理由:
  1. sonnet が勝つのは**別れの締め**と**深い履歴**という、体験上の重みが大きい場面
  2. haiku はダッシュを多用し、TTS 読み上げでは不利
  3. 節約は 26%（$0.1126 → $0.0833 / 36 リクエスト）。1 セッション換算で $0.03 程度、
     **毎日 1 セッションでも月 $1 前後**。上の 2 点を飲む対価としては小さい
- ただし互角と言える水準ではあるので、**将来 sonnet の値上げ（導入価格は 2026-08-31 まで）や
  system prompt の増量（4,096 トークンを超えれば haiku でもキャッシュが効く）があれば再評価する価値がある**
- 生成テキスト全 107 件と判定理由は目視確認用に公開済み

### マルチターン再生（学習者発話を固定し AI ターンだけ再生成）

2 セッション（学習者 5 ターン / 8 ターン）を先頭から通しで再生し、3 ターンずつの窓で A/B。

**sonnet 3 勝 / haiku 1 勝 / 引き分け 1 —— 単発では互角だった haiku が、会話全体では負けた。**

単発ターン評価では見えない差が出た。opus の指摘を要約すると:

- **話題からの逸脱**: haiku は「週末の失敗談」の開幕で「週末はどう過ごす?」と、
  失敗談というテーマから外れた（点差 8-4）
- **かみ合わない質問**: 「毎朝 5 歳の息子にオムレツを作る」という新情報に対し、
  haiku は「息子は面白がった?」と噛み合わない質問を返す（8-5）
- **クローズド質問への偏り**: haiku は「alone or with son」「more than once or first time」など
  選択式が続き、学習者の発話量を引き出しにくい（8-6）
- **規約崩れの再発**: STT ノイズ「Hello.」に対し haiku は「まだいますか？」「大丈夫？」と
  2 連続で問いかけ、「最終行だけが質問」を崩した

**自分の出力が履歴に積まれていくと差が開く**。単発では 1 ターンだけ見るので、
文脈の引き継ぎや話題の維持といった弱点が表に出なかった。

## Phase 3 実施記録（2026-08-01）— フィードバック

### 機械チェック（4 transcript × 3 生成 × 3 モデル）

| モデル | 違反なし | 途中で切れ | フェンス混入 | AI 発話を添削 | transcript 外の添削 |
| --- | --- | --- | --- | --- | --- |
| `claude-sonnet-5` | **10/12** | 0 | 0 | **0** | **0** |
| `claude-haiku-4-5` | 6/12 | 0 | 0 | **0** | **0** |

- **誤りの捏造は 3 モデルとも 0 件**。AI キャラの発話を学習者の誤りとして添削したものも 0。
  これは自動判定できる（原文を正規化して transcript の学習者行に部分一致するか）
- haiku の違反はほぼ**note の文字数超過**（56〜90 字。目安 40 字）。日本語の説明が冗長になる
- Gemma は**フェンス混入 3 件**（トピック生成と同じ癖）と、1 件で
  `stop_reason=RECITATION`（Gemini 側の再生成ブロック）で出力が途切れた

### 仕込んだ誤りの検出率 —— 合成 fixture だからこそ測れる指標

合成 transcript には日本人学習者に典型的な誤りを 21 個仕込んである。
「正解の誤り一覧」があるので**リコールを機械的に測れる**（実データではできない）。

| モデル | 21 件中の検出（3 生成のうち 1 回以上） |
| --- | --- |
| `claude-sonnet-5` | **20 / 21** |
| `gemma-4-31b-it` | 18 / 21 |
| `claude-haiku-4-5` | 17 / 21 |

**決定的だったのは和製英語「mansion」**（日本語のマンション ≠ 英語の mansion = 豪邸）:

| | sonnet-5 | haiku-4-5 | gemma-4-31b-it |
| --- | --- | --- | --- |
| mansion → apartment | **3/3** | **0/3** | **0/3** |

system prompt は「Prefer errors that hurt understanding（理解を妨げる誤りを優先）」と
指示している。三単現の s より、**意味が通じなくなる和製英語のほうが実害が大きい**。
それを毎回拾ったのは sonnet だけだった。日本人学習者向けアプリとしては重い差。

なお検出「回数」を見ると sonnet は 1/3・2/3 が多く、haiku / Gemma は 3/3 が多い。
sonnet は「最も有用な 5 件に絞る」指示に忠実で毎回違う誤りを選ぶのに対し、
haiku / Gemma は同じ誤りを繰り返し拾う傾向がある。**それでも mansion は 3/3 で外さない**。

### そのほか目視で見えた差

- **haiku の note に英語が混入**: 「three person singular の主語には wants と -s をつけます」。
  system prompt は "Write all explanations in Japanese" と指示している
- **haiku の improved が 2 案並記**: 「Someday we'll discuss it or Someday we should discuss it」。
  improved は 1 つの自然な言い方であるべき
- 日本語の自然さ自体は 3 モデルとも実用水準。Gemma も破綻しない（structured outputs 経路なので）

### 料金（12 リクエスト = 4 transcript × 3 生成）

| モデル | 入力 | cache 読 | 出力 | 12 回の実額 |
| --- | --- | --- | --- | --- |

| `claude-haiku-4-5` | 14,763 | 0 | 4,984 | **$0.0397** |
| `gemma-4-31b-it` | 9,309 | — | 3,894 | $0（従量なら $0.0023） |

**フィードバックは会話ターンと違い、haiku が 84% 安い**（$0.2429 → $0.0397）。理由は出力量:
sonnet は `effort: high` で 14,493 トークン出力するのに対し、haiku は effort を送れないので
4,984 トークン。**思考量の差がそのまま単価差に乗る**ので、会話ターン（26% 減）とは桁が違う。

## Phase 4: 経路ごとの採否（2026-08-01 確定）

| 経路 | クオリティ | 料金（1 セッション換算） | 判断 |
| --- | --- | --- | --- |
| 会話ターン | Gemma **失格**（台本形式が成立しない）。haiku は単発 A/B で互角（14-12-4）だが、**再生では 1-3 で負け**、締め・深い履歴で劣り、TTS 向きでないダッシュを多用 | $0.20 → $0.12（**−40%**、月 $2〜3） | **sonnet-5 のまま** |
| トピック生成 | sonnet が明確に上（違反 19/20 対 14/20）。Gemma は語の重複バグ、haiku は hook 冗長・全角半角の混在 | $0.005 → $0.001（月 $0.1〜0.2） | **sonnet-5 のまま** |
| フィードバック | **sonnet だけが和製英語 mansion を 3/3 で検出**。haiku は note に英語混入・文字数超過、Gemma はフェンス混入と RECITATION | $0.06 → $0.01（**−84%**、月 $0.5） | **sonnet-5 のまま** |
| 記憶ノート | sonnet ≒ haiku。Gemma は要約が薄く実用に耐えない | $0.008 → $0.002（月 $0.2） | **sonnet-5 のまま** |

**結論: 4 経路とも `claude-sonnet-5` を維持する。置き換えはしない。**

### 判断の根拠

1. **節約の総額が小さい**。4 経路すべてを haiku にしても **月 $3〜4**。
   1 セッション $0.42 のうち LLM は $0.27 で、残りは STT $0.09 + TTS $0.05。
   会話ターンのキャッシュが効かなくなるぶん、単価 1/3 がそのまま効かない
2. **haiku が落とすものが、このアプリの中核と重なる**。
   和製英語の指摘（学習の質）、別れの締めと文脈の引き継ぎ（会話体験）、
   TTS で読める表記（音声アプリの前提）
3. **Gemma は 2 経路で失格**（会話ターン・記憶ノート）、2 経路で難あり
   （トピックの語重複、フィードバックのフェンス混入）。無料でも採れない

### それでも分かったこと（将来の再評価に効く）

- **haiku は台本規約の遵守だけなら sonnet より上**（実害違反 35/36 対 31/36）。
  弱いのは「規約を守れるか」ではなく「文脈を活かして話を広げられるか」
- **キャッシュ最小長 4,096 は会話ターンの経済性を決定づける**。system prompt が
  4,096 トークンを超える設計に変われば、haiku の節約幅は 26% から大きく改善する
- **effort を送れないことが、フィードバックでは有利に働く**（出力 14,493 → 4,984 トークン）。
  ただし thinking を削った結果として mansion のような発見を落としている可能性がある
- 再評価のトリガ: sonnet-5 の導入価格終了（2026-08-31）、system prompt の増量、
  haiku 系の新モデル、Gemma の台本追従の改善
