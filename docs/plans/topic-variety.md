# トピックが単調なのを改善する

## 目的・背景

トピックカードに出る候補 3 件が毎回似た顔ぶれになる（朝のルーティン / 好きな食べ物 / 週末の予定 / 旅行の思い出 …）。
会話練習としては「話す型」が毎回同じになり、発話量を稼ぐ以上の伸びが出ない。

現状（`EslSpeakingCoach/Claude/TopicSuggestionClient.swift`）の作りから、単調さの原因は 3 つある。

1. **プロンプトのジャンル列挙が狭い**
   system prompt に `daily routines, food, travel, work, hobbies, movies, plans, small personal stories` と
   例示しており、モデルはほぼこの 8 個の中だけを回る。しかも列挙順に引きずられて前方（routine / food）が出やすい。
2. **入力が毎回ほぼ同じで、揺らぎを与える手段がない**
   user メッセージは `Recent topics: …` だけ。`temperature` は本プロジェクトの規約で送れない（sonnet-5 は 400）。
   つまり**リクエスト側に多様性の種が一切入っていない**ので、モデルの最頻出力に収束する。
3. **重複回避が「タイトルの重複」でしか効いていない**
   `Do not repeat or closely resemble any topic in the recent-topics list` は文字列としての近さしか避けられない。
   「朝のルーティン」→「夜のルーティン」→「休日のルーティン」のように、**タイトルは違うが会話の型が同じ**候補は素通りする。
   直近 20 件（`ChatHistoryStore.recentTopicTitles`）を渡してもここは埋まらない。

よって「プロンプトを強く書く」だけでは不足で、**アプリ側から多様性の種を注入する**のが本筋。

## 対応方針

### 方針 A（採用）: ジャンル × 話し方の軸をアプリ側でサンプリングして注入する

リクエストごとに、アプリが持つカタログから**ジャンル 3 件**と**話し方（会話の型）3 件**を
ランダムに引き、「候補 1 はこのジャンル・この型で」と割り当てて user メッセージに載せる。
モデルの自由度を残しつつ、出力の分布をアプリ側が制御できる。

- **ジャンルカタログ（20〜30 件）**: 現行 8 件を核に広げる。例
  食 / 旅 / 仕事・勉強 / 趣味 / 映画・音楽・本 / 季節と天気 / 買い物と持ち物 / 街と近所 / 家事と暮らし /
  健康と運動 / お金の使い方 / テクノロジーとアプリ / 子どもの頃の思い出 / 家族と友だち / ペットと動物 /
  失敗談・ハプニング / 習慣を変えた話 / 苦手なもの / 憧れ・やってみたいこと / ちょっとした自慢 /
  もしもの想像 / ニュースで見かけた話 / スポーツ / ゲーム / 乗り物と移動 / 眠りと朝晩
- **話し方カタログ（6〜8 件）**: これが効く。同じ「食」でも型が変われば発話の質が変わる
  思い出を語る（過去形） / 説明する（手順・やり方） / 比べて選ぶ（比較級） / 意見を言う（賛否） /
  想像する（仮定法・if） / 計画を立てる（未来形） / 描写する（今見えているもの） / 教える・すすめる
- 3 件それぞれに**別のジャンル・別の型**を割り当てるので、1 カードの中の多様性も担保される
- 難易度も 3 件で散らす（やさしい 1 / ふつう 1 / すこし挑戦 1）を明示

ランダム性は `SystemRandomNumberGenerator` ではなく**注入可能な RNG** にして、テストで固定シードを使えるようにする。

### 方針 B（同時に入れる）: 直近の「ジャンル」も覚えて避ける

タイトル文字列だけでなく、**そのセッションで使ったジャンル**を履歴に持ち、
サンプリング時に直近 N 件で使ったジャンルを除外する。これで「タイトルは違うが同ジャンル」の連発が止まる。

- `ChatSessionRecord` に `topicGenre: String?` を additive で追加（既存ストアはそのまま開ける）
- 自作トピック・フリートークは `nil`（ジャンル不明）とし、除外対象にしない
- 除外しきってカタログが尽きる場合はリセットして全件から引く（候補ゼロを避ける）

### 方針 C（検討のみ・今回は入れない）: 記憶ノートから興味を引く

`CharacterMemoryStore` のノートには学習者の仕事・趣味などが溜まっている。これを種にすると
「自分ごと」のトピックが出せるが、**逆に同じ興味へ収束して単調さが悪化するリスク**がある。
方針 A / B を入れた後に効果を見てから判断する。今回はスコープ外として記録だけ残す。

### 副次: 仕様書のドリフト修正

`docs/specs/conversation-design.md` の「トピック生成」は各候補を **英語タイトル（3〜6 語）+ フック 1 文（12 語以内）**
と書いているが、実装は**日本語タイトル + 日本語フック**（付録 B の system prompt どおり）。
実装が正なので本文側を日本語に直す。

## Phase / Step

- **Phase 1: カタログとサンプラー**
  `TopicCatalog`（ジャンル / 話し方 / 難易度）と、直近ジャンルを除外して 3 件を引くサンプラーを追加。RNG は注入可能。単体テストのみで完結。
- **Phase 2: プロンプト・リクエストへの反映**
  `TopicSuggestionClient` の system prompt を書き換え、`makeRequestBody` に割り当てを載せる。
  スキーマに `genre` を追加して候補がどのジャンルとして生成されたかを受け取る。
- **Phase 3: 履歴へのジャンル永続化**
  `ChatSessionRecord.topicGenre` を追加し、セッション開始時に保存 → 起動時に `recentTopicGenres` を復元してサンプラーへ渡す。
- **Phase 4: 実機・シミュレータ確認と仕様書同期**
  シミュレータで 🔄 を数回叩いて候補の散り方を目視確認 → `conversation-design.md` を同期 → プランを archive へ、TODO を DONE へ。

## テスト方針

- **単体（新規）**
  - サンプラー: 固定シード RNG で 3 件が**すべて別ジャンル・別の話し方**になること
  - サンプラー: 直近ジャンルが除外されること / 除外しきったらリセットして必ず 3 件返すこと
  - `makeRequestBody`: user メッセージに割り当て 3 件が含まれること、`temperature` / `top_p` / `top_k` を送らないこと（既存規約テストを維持）
  - `parseResponse`: `genre` 付き応答を読めること、`genre` 欠落でも従来どおり壊れないこと
- **単体（既存）**
  - `TopicSuggestionClientTests` の user メッセージ期待値（`Recent topics: …` 完全一致）は形式変更に合わせて更新する
  - `ChatHistoryStoreTests` にジャンル保存・取得のケースを追加。既存ストアを開けること（additive）を確認
- **手動（シミュレータ）**
  - 🔄「他の候補」を 5〜6 回連続で叩き、ジャンルが繰り返さず型も散ることを目視
  - セッションを 2〜3 本回して、次のカードに直前セッションと同ジャンルが出ないこと
- 実機でしか見られない要素はないため、シミュレータ確認までを完了条件とする（実機未確認である旨は明示する）

## 未確定・判断が要る点

- ジャンルの割り当てをどこまで強制するか。強制しすぎると「無理やり感のあるトピック」が出るおそれがある。
  まずは**ヒントとして提示 + 3 件は必ず別ジャンル**の強さで実装し、出力を見て締める / 緩める
- カタログを Swift のコード内定数にするか JSON リソースにするか。個人ツールなので**コード内定数**で始める
